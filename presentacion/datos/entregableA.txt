1.3 Restricciones
Tipo
Descripción
Tecnológicas
Base de datos PostgreSQL + PostGIS; backend Python + Django; frontend React; despliegue en AWS (S3+CloudFront, Elastic Beanstalk, RDS, CloudWatch).
Regulatorias
Cumplimiento EUDR (certificado de no deforestación); certificación de origen Nariño; solo productores de Colombia (no Ecuador).
De negocio
Sin inventario (intermediarios); comisión del 1% con valor mínimo; cantidad mínima de 100 kg por lote.
De alcance (primera entrega)
Sin pasarela de pago real (escrow simulado por máquina de estados); sin logística real, solo tracker de estados.
De proceso
Sprints de 2 semanas, releases mensuales, entrega por módulos funcionales con aprobación del stakeholder.
De idioma
Compradores de la Unión Europea; el soporte multi-idioma queda como requisito pendiente.

2.2 Vista de contexto
El sistema RiTech SAS actúa como intermediario digital entre los productores de café/cacao de Nariño y los compradores de la Unión Europea, integrando servicios externos de calidad, custodia del dinero (escrow simulado) y autoridades aduaneras.

2.3 Vista funcional (componentes: lollipop y sockets)
El sistema se organiza en módulos de negocio (apps de Django). Cada módulo provee una interfaz de API (lollipop) y consume las interfaces que necesita (socket). La Web UI (React) consume todas las APIs; la persistencia se resuelve con PostgreSQL + PostGIS y los archivos con S3.

2.5 Casos de uso detallados
CU-09 Publicar lote de café/cacao
Actor: Vendedor
Precondición: El vendedor tiene sesión activa, perfil completo y finca con certificados vigentes (estado EUDR habilitada).
Flujo principal: 1. El vendedor entra a 'Publicar lote'. 2. Ingresa producto, origen, cantidad y precio (fijo o a acordar). 3. El sistema valida cantidad ≥ 100 kg (RN-1) y origen permitido (RN-10). 4. El sistema crea el lote en estado PUBLICADO. 5. El lote queda visible en el marketplace.
Postcondición: Lote publicado; los compradores pueden encontrarlo y negociar.

CU-12 Acordar transacción inmutable
Actor: Comprador y Vendedor
Precondición: Existe una negociación activa con un lote publicado y disponible.
Flujo principal: 1. Las partes acuerdan precio. 2. El sistema crea la transacción con el precio acordado y calcula la comisión (1% con mínimo). 3. Marca la transacción como inmutable (RN-6). 4. Bloquea el dinero en escrow. 5. El lote pasa a VENDIDO.
Postcondición: Transacción creada e inmutable; dinero bloqueado; cualquier cambio posterior requiere disputa.

CU-17 Verificar calidad muestra vs. producto
Actor: Comprador
Precondición: Existe una transacción con muestra registrada y producto recibido.
Flujo principal: 1. El comprador abre la verificación de calidad. 2. Compara el producto recibido contra la muestra usando los parámetros del laboratorio (RN-9). 3. Emite el veredicto ACEPTA o RECHAZA.
Postcondición: Veredicto registrado; si ACEPTA se libera el pago, si RECHAZA se abre disputa.

CU-19 Actualizar estados del pedido
Actor: Transportador
Precondición: Existe un envío asociado a una transacción.
Flujo principal: 1. El transportador actualiza el estado del pedido. 2. El sistema registra el evento con fecha y observación. 3. Comprador y vendedor ven el tracker actualizado.
Postcondición: Tracker actualizado con el historial de estados.

4. Épicas e historias de usuario con criterios de aceptación
4.1 Épicas (módulos)
LIT-57 — M1: Usuarios y seguridad  (Sprint 1)
Todos los roles pueden autenticarse y solo acceden a sus funciones.
La identidad se verifica y los usuarios fraudulentos se bloquean.
La información privada nunca se expone entre usuarios.

LIT-58 — M2: Fincas y trazabilidad EUDR  (Sprint 2)
La finca se registra con geolocalización y área.
Los certificados se cargan con vigencia y validación.
El estado EUDR se calcula y bloquea fincas sin certificados vigentes.

LIT-59 — M3: Marketplace  (Sprint 3)
Se publican lotes con cantidad ≥ 100 kg y precio válido.
El comprador busca, filtra y negocia por chat.
El acuerdo genera una transacción inmutable.

LIT-60 — M4: Transacciones y escrow  (Sprint 4)
El dinero se bloquea y solo se libera al aceptar el producto.
La comisión del 1% con mínimo se calcula correctamente.
Las disputas se gestionan por el administrador.

LIT-61 — M5: Calidad  (Sprint 5)
La muestra se registra y se compara con el producto recibido.
El veredicto del comprador libera o retiene el pago.

LIT-62 — M6: Logística (tracker)  (Sprint 5)
El transportador actualiza los estados del pedido.
El tracker es visible para comprador y vendedor.

LIT-63 — M7: Administración  (Sprint 6)
El admin del sistema gestiona usuarios, disputas y comisiones.
El admin técnico audita y respalda.
La plataforma se despliega en AWS y cumple los RNF.

4.2 Historias de usuario y criterios de aceptación
LIT-64 — Registro y login de usuarios por rol   [Épica LIT-57 · Sprint 1]
El usuario se registra con nombre, identificación, email y firma una sola vez (RN-5).
El login valida credenciales y devuelve acceso según el rol.
Un usuario no puede ejecutar funciones fuera de su rol (RN-13).

LIT-65 — Verificación de identidad de usuarios   [Épica LIT-57 · Sprint 1]
El sistema valida identificación y firma antes de habilitar operaciones.
Un usuario no verificado no puede publicar lotes ni comprar.

LIT-66 — Privacidad de información entre usuarios   [Épica LIT-57 · Sprint 1]
La ubicación y datos de fincas permanecen ocultos hasta una negociación activa (RN-13).
Ningún endpoint expone datos privados de otro usuario.

LIT-67 — Bloqueo y baneo de usuarios por fraude   [Épica LIT-57 · Sprint 1]
El administrador puede bloquear y desbloquear usuarios (RN-12).
Un usuario bloqueado no puede iniciar sesión ni operar.

LIT-68 — Registro de fincas con geolocalización   [Épica LIT-58 · Sprint 2]
El propietario registra la finca con polígono (PostGIS) y área.
El sistema valida que el origen sea Nariño/Colombia (RN-2, RN-10).

LIT-69 — Carga de certificados de la finca   [Épica LIT-58 · Sprint 2]
Se cargan certificados de origen Nariño, no deforestación y orgánico con archivo y vigencia (RN-3).
Un certificado vencido marca la finca como bloqueada.

LIT-70 — Estado de cumplimiento EUDR por finca   [Épica LIT-58 · Sprint 2]
La finca muestra estado HABILITADA o BLOQUEADA según sus certificados vigentes.
Una finca bloqueada no puede publicar lotes.

LIT-71 — Perfil del vendedor   [Épica LIT-58 · Sprint 2]
El vendedor registra capacidad de producción, tipo de producto, variedad y calidad comprometida.
El perfil se reutiliza en cada publicación.

LIT-72 — Publicación de lotes de café/cacao   [Épica LIT-59 · Sprint 3]
La cantidad mínima del lote es de 100 kg (RN-1).
El precio puede ser fijo o 'a acordar' (RN-4).
Solo vendedores con finca y certificados válidos pueden publicar.

LIT-73 — Búsqueda y filtros de lotes para compradores   [Épica LIT-59 · Sprint 3]
El comprador filtra por producto, origen, cantidad y precio.
Los resultados ocultan los datos privados del vendedor.

LIT-74 — Chat de negociación comprador-vendedor   [Épica LIT-59 · Sprint 3]
Los mensajes se intercambian dentro de una negociación.
La información privada se revela solo dentro de la negociación activa.

LIT-75 — Transacción de venta inmutable   [Épica LIT-59 · Sprint 3]
Al acordar, se crea la transacción y no admite modificaciones (RN-6).
Cualquier cambio posterior pasa por disputa.

LIT-76 — Dinero bloqueado (escrow) hasta aceptación   [Épica LIT-60 · Sprint 4]
El dinero se bloquea y solo se libera al aceptar el producto (RN-7).
El escrow maneja los estados BLOQUEADO, LIBERADO y DEVUELTO.

LIT-77 — Cálculo de comisiones (1% con valor mínimo)   [Épica LIT-60 · Sprint 4]
La comisión del 1% con valor mínimo se calcula para comprador y vendedor (RN-11).
El cálculo es exacto y visible en la transacción.

LIT-78 — Gestión de disputas   [Épica LIT-60 · Sprint 4]
El administrador gestiona la disputa con motivo, estado y resolución.
Una disputa abierta congela la liberación del pago.

LIT-79 — Registro de muestra del producto   [Épica LIT-61 · Sprint 5]
El propietario/vendedor registra la muestra del producto (RN-8).
La muestra queda asociada a la transacción.

LIT-80 — Verificación de calidad muestra vs. producto recibido   [Épica LIT-61 · Sprint 5]
El comprador compara el producto recibido con la muestra.
Se usan los parámetros definidos por el laboratorio de café (RN-9).

LIT-81 — Veredicto del comprador libera el pago   [Épica LIT-61 · Sprint 5]
Si el comprador acepta, se libera el escrow al vendedor.
Si rechaza, se abre una disputa.

LIT-82 — Actualización de estados del pedido por el transportador   [Épica LIT-62 · Sprint 5]
El transportador actualiza los estados (preparado → enviado → en tránsito → entregado) (RN-14).
Cada cambio registra fecha y observación.

LIT-83 — Tracker del pedido visible para comprador y vendedor   [Épica LIT-62 · Sprint 5]
Comprador y vendedor ven el historial de estados del pedido.
El tracker solo muestra pedidos de la propia transacción.

LIT-84 — Panel del administrador del sistema   [Épica LIT-63 · Sprint 6]
El admin gestiona usuarios, disputas, bloqueos y comisiones.
Toda acción administrativa queda registrada.

LIT-85 — Panel del administrador técnico (auditoría y respaldos)   [Épica LIT-63 · Sprint 6]
El admin técnico consulta la auditoría de acciones.
Puede verificar el estado de los respaldos en AWS.

LIT-86 — Despliegue de la plataforma en AWS   [Épica LIT-63 · Sprint 6]
El frontend React se sirve desde S3 + CloudFront.
El backend Django corre en Elastic Beanstalk con RDS PostgreSQL + PostGIS.

LIT-87 — Requisitos no funcionales de la plataforma   [Épica LIT-63 · Sprint 6]
Se verifican los RNF (exactitud, usabilidad, fiabilidad, mantenibilidad, seguridad y respaldo) antes de cada release.
Los resultados quedan registrados en el plan de pruebas.
